# Building Polydeukes in Public #8 — One CLI that knows no agent, and the tag that would not stay annotated

**English** · [한국어](./2026-09-v0.7-entrypoint-reshape.ko.md)

> *v0.7.0 · the umbrella package now exposes one executable and one JSON file, and nothing
> to `import`. Judgment reaches it as an IR on stdin or as a unified diff, and leaves as an
> exit code. Each coding agent's hook is its own installable adapter; programs call a
> TypeScript SDK that spawns the CLI and returns the verdict as a value. Disciplines moved
> into the list of the surface that can observe them. Post #6 promised the advise delivery
> measurement and the external install evidence; this post reports that neither moved, and why
> the gate's own paperwork failed for the fourth time in a row.*

v0.7.0 closed on 2026-09-15 with eight tickets — seven `SURFACE-*` and one `COVENANT-22`
that landed in the same window. The design goal was stated in one sentence at the start:
the umbrella knows no coding agent and no version-control system. What follows is what
that cost, what it measured, and what it did not deliver.

## What shipped: a process protocol, and three kinds of client

The public shape of `polydeukes` is now `pdks covenant check [--diff] [--enforce advise|block]`.
Its stdin is either the IR — the same input the session hook used to assemble in-process —
or a unified diff, which the umbrella translates itself. Its output is an exit code and a
`why` on stderr. The package's `exports` map has one entry, the JSON schema; `main`,
`module`, `types` and the `.` barrel are gone, and `import 'polydeukes'` is an
`ERR_PACKAGE_PATH_NOT_EXPORTED`. The judge lives inside the umbrella as `src/covenant/`
(seventy-two files renamed, bodies unchanged), and `@polydeukes/core` stays as the
vocabulary package that adapters and the SDK import the IR types from.

Three kinds of client talk to that protocol:

- **An adapter per agent** — `@polydeukes/adapter-claude-code` and `@polydeukes/adapter-grok`.
  Each is one install unit: its `init` bin registers the hook, its `runHook` builds the IR
  from that host's payload and spawns `pdks covenant check --enforce block`. Zero lines of
  judgment. Both take the umbrella and core as peer dependencies and nothing as a
  dependency; the umbrella depends on neither. The dependency arrow was reversed in this
  milestone — before it, the umbrella pulled the adapters in.
- **The SDK** — `@polydeukes/sdk-ts` exposes one verb, `checkCovenant(spec)`, which finds
  `pdks` in the caller's install graph, spawns it, and returns `upheld`, `blocked` or
  `unjudged` as a value with the reason text. Its first intended consumer is an unattended
  LLM pipeline whose path boundary is currently enforced only by a prompt.
- **A change-set producer** — this repository's lefthook line pipes `git diff --cached`
  into `pdks covenant check --diff`. Any producer of a unified diff — git, jj, hg, a hand
  — is the same surface. The `/dev/tty` prompt the commit path used to open is gone; the
  domain in which the criterion "zero code opens `/dev/tty`" was measured is every package
  source and test, both hook directories, and the lefthook file.

The last ticket split the discipline list in three by observation channel: `disciplines`
for entries both surfaces can judge, `sessionDisciplines` for entries that read the command
line, the transcript, the spawn sidecar or the actor, `changeSetDisciplines` for entries
that read the whole change set. The loader refuses an entry written in a list whose surface
cannot observe its channels. The word "commit surface" was replaced throughout by
"change-set surface", because the surface is defined by its input, not by git.

This repository is now judged by the install units it ships: the two hook delegators in
the tree are byte-identical to what the two adapters' installers write, and a test runs
both installers and diffs the result. The rewiring exposed three defects the old in-process
path had been hiding, the worst of which was a `passed` row written for a call nothing had
judged on a host that proves no session. That is the defect class the telemetry vocabulary
exists to name, and it had shipped for one commit.

## The gate audited its own grading sheet, for the fourth time

Same form as the last three gates: this session re-ran every criterion as a command, and an
independent adversarial reviewer re-read the criteria sentences. Code blockers: zero — 2,708
tests across five packages, both surfaces producing live telemetry rows on demand. Sentence
defects: **eleven**, in seven sentences. Two "text oracle" criteria were wider than the oracle
that enforces them (the umbrella source does contain the string `.claude/hooks` in a
scaffold template and `'git status'` in a shell allowlist; the oracles check tool rosters
and spawn spellings, not substrings). A criterion demanded "one row per surface" from a log
that has no surface column. The ticket count "seven" and the range "`SURFACE-01`–`05`"
named different sets. A "fixture" the SDK criterion cited does not exist. The `--diff`
parity count was off by one. And so on — every sentence was corrected to name the oracle's
actual domain, and the corrected text is what the history entry inherited.

The audit found three defects outside the criteria and fixed them before the release: the
`/dev/tty` oracle did not scan the Grok delegator directory; nothing asserted the adapters'
`dependencies` field is empty; two comments described the pre-reshape dependency graph.
The fix's first CI run failed on a type the test file did not declare — vitest does not
typecheck, so the assertion had passed locally against a field the type did not know.

## Round three: the falsification clause, unanswered

**Advise consumption: 45/154 = 29.2%.** Third consecutive round below half. Post #6 said the
next step was a ticket measuring which channel an advisory actually reaches the model
through. That ticket was not opened — every v0.7.0 ticket was the reshape — so this is the
same falsification repeated, not a new one, and the judgment stands: the evidence does not
justify restoring blocking as the default.

What the round added is a correction to the metric. Three disciplines that judge *who* did
something — a commit by a subagent, a test file written by the implementer, a merge with no
fresh instruction — produced their first natural rows this window: 26, 10 and 9. They cannot
be "consumed" by a later `passed` on the same subject, because only a human's new
instruction resolves them, so they do not belong in the consumption denominator. Excluding
them the ratio is 39.6%, level with round two. And one of the nine unlicensed merges was
this gate session merging the audit-fix PR under an instruction that did not name a merge —
the discipline read the instruction correctly.

The other gate indicator held for the third round: of 215 natural blocks, 92% were the
judging chain protecting itself and 16 were the two disciplines that opted into blocking.
The audit session was refused six times for read-only commands that mentioned a protected
path; four were traceable to specific commands, and all four were reads. A 1,429-row batch
from a development session on 2026-09-08 — block counts of exactly 30, 36 and 50 per label —
was excluded as a fixture run, after measuring that the shipped suite writes zero rows to
the live log.

## The reader we finally met

The reader six-task test — deferred from v0.6.1 because the reshape would change the install
shape — ran in this gate. Two reviewers who had never seen the project, one reading only the
English documentation and one only the Korean, each had to install, write a discipline,
recover from an error, look up an option, call the SDK, and look up a search result, using
the docs alone and recording where they got stuck. Since 0.7.0 was not yet on npm, they
installed from the packed tarballs and were told to flag every place that substitution made
an instruction ambiguous.

Both got stuck in the same place, and it was the only place either was actually stopped:
the install line. Eight of the nine places the docs give an install command list the
umbrella and the adapter; the adapter also declares `@polydeukes/core` as a peer, and only
the SDK reference lists all three. On a registry install npm resolves that peer itself, so
the line would have worked; from tarballs it fails with `ETARGET`, and the inconsistency
across the repository is real either way. Both readers then completed every other task.
Both also flagged the same three time costs — the `pdks explain` reference's example output
predates the change that turned the shell meta-covenant into a `skip` row on a fresh config;
the tutorial requires pnpm while four reference pages use npm; the SDK page never says the
package is ESM-only, so the example fails as a `.js` file in the tutorial's own project.

Each reader also found something the other did not. The Korean reader noticed that the
discipline how-to says to save its complete YAML as the config file, and that YAML carries no
`protectedPaths` and no `witness` block — follow it literally over a generated config and
the witness valve is gone. The English reader found the configuration reference's witness
example still showing a token the installer stopped generating, a troubleshooting sentence
that attributes a message prefix to the session hook when the judge writes it on both
surfaces, and a tutorial that names an artifact by description rather than by path. Seven of
these were fixed the same day; the rest are the next documentation ticket's material. The
Korean reader's search queries both returned the right section first; one of the English
reader's did not, and the docs say up front that the search is deterministic text matching.

One observation from outside the task's domain: both reviewers' sandbox work was refused
several times by *this* repository's session hook — a `find` that mentioned `.git/hooks`, a
`node` command line that mentioned `.claude/hooks`, a redirect into a config file. A reader
who runs the tutorial's commands inside another project that already has pdks wired will
meet the same refusals.

## Release footnote

Release-please produced the 0.7.0 release PR without a `Release-As` footer, since the
branch carried breaking `feat!` commits, and the CHANGELOG link rewrite added at v0.6.0
worked. Tag `v0.7.0` was cut at `06567a1`. The annotated-tag reversion first seen at v0.6.0
reproduced exactly: the workflow's force-push of the annotated tag was accepted, and the
ref pointed at the bare commit again immediately after; `v0.6.1` is in the same state. The
gate session could not re-push the annotated tag because the repository's own
`work-stays-recoverable` discipline blocks force-pushes and its valve is a human's witness
token — the discipline did its job on its author. Three releases in a row now; the
annotation step itself is the suspect.

The npm publish did not happen at v0.7.0. The publish workflow runs the full suite before
uploading, and the clean-install e2e — which claimed its consumer tree never touched the
registry — was measured resolving the umbrella's dependency on core from the registry,
where the current version does not exist until the publish it gates. Every earlier release
had passed that suite only because the registry already carried the same version. Two
dispatches on the tag failed on it. The fix (the consumer also names core as a direct
tarball dependency) went in as a `fix:` commit, release-please cut 0.7.1, and that tag's
publish uploaded three of the five packages before stopping at `@polydeukes/adapter-grok`
with `ENEEDAUTH`: npm trusted publishing is configured per package, and the two packages
this milestone created had never been published, so their first upload needs the owner's
token. So v0.7.0 is a tag and a release with no npm artifact; 0.7.1 is the reshape's first
npm version; and at the time of writing `@polydeukes/adapter-grok` and `@polydeukes/sdk-ts`
await that first manual publish.
