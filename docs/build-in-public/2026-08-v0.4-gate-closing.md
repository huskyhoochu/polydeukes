# Building Polydeukes in Public #4 — Closing the release, paying one receipt and rescheduling the other on the record

**English** · [한국어](./2026-08-v0.4-gate-closing.ko.md)

> *v0.4.0 · six tickets of defects, debts and documentation; the first tokenless publish with
> provenance on all five packages and the `NPM_TOKEN` secret deleted; and the real-install
> receipt — owed since post #2 — rescheduled to after the algebra refoundation, with its
> domain and its done-condition written down instead of a date-shaped promise.*

Post #3 ended with a confession: we called v0.3.0 "installable" without having installed it
anywhere but our own machines, and we promised evidence in the next post.
v0.4.0 added no new judging capability. Its six tickets addressed defects, debts, and
documentation, and completed one of those two commitments. The other has been rescheduled
as described below.

## Receipt one: the real install, rescheduled on the record

There is still no out-of-repository install to cite. Instead of deferring it to "next post" a
third time, the owner made it a scheduling decision: **the real-install measurement moves to
after v0.7.0** — the far end of the two algebra-refoundation milestones. The reasoning is in
the roadmap's own sequence: v0.5.0 through v0.7.0 change the default posture (advise-first),
the judging path (one engine over a relation algebra), and what `pdks init` writes. The
project chose to measure the surface consumers will actually get, once, rather than the
surface being replaced, twice.

The deferral specifies a domain and a done-condition rather than another publication date. Domain:
one real
project outside this repository, install → `pdks init claude-code` → one real judgment, plus
one layout observation (whether the generated config carries a `$schema` line). Done when: the
telemetry rows and exit codes are quoted in a future post of this series. Until that quote
exists, the claim "polydeukes is installable in the wild" remains what it has been since
post #3: unverified, and labeled as such.

## Receipt two: a publish with no token

The token-free publish succeeded. The v0.4.0 release chain ran end to end on 2026-08-18:
release PR #59 squash-merged on the Forgejo origin, the release-please port cut the tag, the
push mirror carried `main` and tags to GitHub, and one manual dispatch —
`gh workflow run publish.yml --ref v0.4.0` — did the upload. The run
succeeded in 1m9s. All five packages are on npm at `0.4.0` with SLSA v1 provenance
attestations — which `0.3.0` never had, because `0.3.0` was published by hand from a local
terminal after the CI upload died on `EOTP` (post #3's story). And the fallback that made the
hand-publish possible is gone: the `NPM_TOKEN` secret is deleted, and the repository's secret
list is empty. The registry now trusts the workflow's identity, not a string we store.

One qualification: the *first* dispatch of this same workflow, for v0.3.0 on 2026-08-10,
failed. The tokenless path was proven on its second release, not its first.

## What v0.4.0 actually was

Six tickets, none of them a feature. Together, they addressed inaccurate or incomplete bookkeeping
around the judge.

- **A sixth telemetry word nobody's judgment writes.** The session surface now compares the
  protected entries' on-disk state against a stored baseline at every hook call. A protected
  file that changed with no judgment row explaining it lands one `unattributed` row
  (COVENANT-14). This replaced an arms race we declined to run: instead of chasing every
  spelling of indirect execution (`python3 x.py`, test runners' child processes, `cd`
  prefixes), the surface observes *results*. A rebuild no judgment explains is a true
  positive, not noise.
- **The commit surface's silent-failure window.** A config-load failure used to block the
  commit without leaving a record — fail-closed, but unrecorded (ADAPTER-git-b). The
  asymmetry turned out to be two defects, and the second one — the telemetry append helper
  could not create its own directory, a failure consumers encounter immediately after
  `pdks init` — was caught by the test audit *before* the implementation existed.
- **Config validation that refuses earlier and names more.** Command-family patterns judged
  as line-and-whole-string union, empty-string rejection in five positions, all problems
  enumerated before `loadConfig` returns (CONFIG-09).
- **A schema your editor can actually find.** The umbrella package now bundles the config
  schema and exposes it as a subpath, and `pdks init` writes the `$schema` line only when
  the file is really where the line says (DIST-05 — review measurement corrected our
  assumption about how editors resolve the path).
- **Documentation restructured for the reader that arrives first: an agent.** The README's
  first screen now answers what an AI partner needs before anything else — what this is,
  the three commands, and that `pdks docs` answers offline from the installed version. The
  283-line config reference moved out of the guide into its own reference document, and the
  docs are grouped in three layers (getting started / guides / reference). The `pdks docs`
  topics survived unchanged (DOCS-04).
- Plus a duplication-and-orphan cleanup round (CLEANUP-01) whose audit table recorded which
  of its 13 findings were real (9), misdiagnosed (3), or narrowed (2).

*(Editor's note, 2026-09-06: those three figures sum to 14, not 13. The archived CLEANUP-01
PRD's summary line reads real 9 · resolved-or-misdiagnosed 3 · narrowed 1, and its per-finding
table uses further labels (out of scope, unverified, reinterpreted), so the three categories
above are not a partition of the 13. Read them as the labels the audit applied, not as a count
that reconciles.)*

## The decision that reshapes what comes next

Mid-milestone, the journal's findings led to a decision: **diagnosis
before blocking**. Real-time blocking narrows to the judging chain's self-protection; user
disciplines land as `advise` by default on both surfaces; and the relation algebra becomes
the only judging path over the next two milestones. The lock-vs-CCTV argument from post #1 is
reflected in that default. The measured basis: across the
dogfooding corpus, blocking's prevention record on user disciplines was effectively zero,
while the record→knowledge chain (telemetry rows becoming dev-logs becoming design) is
where the value showed up. v0.5.0 makes that posture official.

## Infrastructure footnote: the forge moved

Development moved off GitHub onto a self-hosted Forgejo; GitHub remains as a mirror with
exactly one job — the npm upload, because trusted publishing (OIDC provenance) is a
github.com property. CI and release automation run on the Forgejo origin now, via a
release-please port that speaks its API. The migration's operational surprises (an imported
bot PR colliding with the port's PR creation, among others) went to the internal dev-log;
the workflows' header comments document the differences.

## What we owe next

The v0.5.0 milestone starts the diagnostic pivot in earnest: `pdks explain`, `why` on every
block message, per-entry enforcement levels, and the advise-consumption metric — the ratio
of advised rows later re-observed as passed — becomes a gate indicator. The falsification
promise for post #5: the pivot's two measurements, reported with their denominators. The
real-install measurement remains scheduled for after v0.7.0. The post following that milestone
will report the evidence or explain why the measurement is still incomplete.
