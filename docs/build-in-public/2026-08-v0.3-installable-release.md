# Building Polydeukes in Public #3 — The release stopped exactly where the plan said it could not be tested

**English** · [한국어](./2026-08-v0.3-installable-release.ko.md)

> *v0.3 · five packages reach npm, the merge-equals-publish pipeline halts at its very last
> step on a registry policy three days older than its own token, and the flagship debt from
> post #2 — the first real-project install — stays open, said out loud.*

Post #2 ended with one bundled commitment: npm publication, a clean-environment install e2e in
front of every upload, `pdks init claude-code`, user docs that treat the two surfaces as two
situations — and, as the flagship claim, the first out-of-repository *real-project* install
judging real payloads, rows and exit codes cited. The escape clause was written next to it: if
the install e2e cannot be shown, post #3 says so.

Here is the accounting, up front. The first four are payable and this post pays them. The
flagship claim is not — the real-project install has not happened, and this post says so in
its own section rather than in a footnote. What fills the space instead is a stranger story:
the publish pipeline passed every gate it could test and stopped at the one step its own PRD
had declared unverifiable by code.

## What v0.3 actually shipped

v0.2 was the release line where users declare disciplines. v0.3 is the line where the thing
becomes installable — and where the artifact that judges us becomes the artifact we ship.

- **The judged artifact is the shipped artifact.** The session surface's assembly moved out of
  this repository's hook file and into a packaged entry point, `runClaudeCodeHook`. Our own
  hook is now a thin delegator calling that entry point through the package's subpath — the
  same import a consumer gets. The ticket's success criterion was *identity*, not improvement:
  on a pass payload and a block payload, the telemetry row, the exit code, and the block
  reason had to be identical to what the old hook produced. They were. Since then, what
  judges every edit in this repository daily is the thing `npm install` delivers.
- **One command wires a consumer project.** `pdks init claude-code` creates four artifacts —
  the hook delegator, the `PreToolUse` registration merged into `.claude/settings.json`, a
  config scaffold, and a `.gitignore` line for the telemetry directory — and overwrites
  nothing: whatever exists is left in place and reported. The sharpest edge is the config
  check. The loader accepts three file names and fails closed on ambiguity, so a scaffold
  that checked only the canonical name could add a second config to a project that already
  has one — and every call in that project would block from that moment on. The check
  therefore looks for all three names, and two or more present is a precondition failure that
  creates nothing. A scaffold must not brick the project it was invited into.
- **A clean-environment install e2e stands in front of every upload.** Two test layers ship
  with the pipeline. Pack verification opens the five tarballs and compares their contents
  against an enumerated list — LICENSE bodies included — and requires zero `workspace:` or
  `catalog:` ranges in the packed manifests. The install e2e then builds the five tarballs,
  installs them into a temporary project outside the repository, runs `init`, spawns the
  generated hook on one pass payload and one block payload, opens the witness valve once (the
  row must read `witnessed`), and measures the `$schema` consumer path. Both layers run
  before the publish step in the release workflow, and PR CI runs the same gates earlier.
- **Three layers of docs, and a discovery path for the AI partner.** Install and
  troubleshooting guides landed first, treating the two surfaces as two situations — the
  session surface for a project developed with an AI partner, the commit surface for a human
  applying discipline to their own commits. A per-package reference layer followed: five
  documents, one per package plus the umbrella. Then the docs became part of the artifact:
  eight English documents travel inside the package, and `pdks docs` answers five topic
  queries — install, config, discipline, covenant, witness — offline, from the local
  executable. `init` gained a fifth artifact for exactly this: a rule file telling the AI
  partner that official answers come from the local binary, not from a web search. One
  continuity note: the reference work replaced the last universal sentence in the
  configuration doc with a two-layer statement — the finite-domain rule post #2 wrote down is
  now editing the documentation.

## The publish that stopped at the last step

The design was merge-equals-publish: release-please computes the version, the release PR
merges, the publish workflow checks tag consistency, does a frozen install, builds, runs every
package's tests, and uploads. Getting to the merge took a detour — the GitHub Actions queue
had been backed up since 08-04 (one test run sat queued for four days without a job
assignment; one push created no run at all), which left the release PR conflicting. The fix
was a rerun of the last release-please run: it reads the branch's current state through the
API rather than a checkout SHA, so a rerun alone recalculates the PR.

Then the workflow ran, passed every gate in front of the upload, and stopped at the first
package with `EOTP` — the registry asked for a one-time password no CI run can type.

The date matters. npm restricted 2FA-bypassing granular tokens from 2026-07-31 — sensitive
operations, new-package creation included — on the way to removing token publishing outright
in January 2027. Our `NPM_TOKEN` was issued on 2026-08-03, three days after the restriction
took effect. All three preconditions the plan listed — scope ownership, token, repository
secret — had been checked and were present. What could not be checked was the one thing they
existed for. The archived PRD's own §3-e had drawn the line in advance: publish capability
*cannot be verified by code* before a real publish. The failure landed exactly inside that
declared region, and fail-closed held — the registry stayed empty rather than half-filled.

Two dispositions followed. First, the initial publish was done by a human: the `v0.3.0` tag
checked out in a separate worktree, the same gate order as CI, `pnpm -r publish`, the OTP
typed by hand. Five packages listed; the four new names took about three minutes to become
readable while the pre-existing umbrella updated instantly. Because `0.3.0` was published
outside CI, it carries no provenance — that is a fact about this version, permanently.

Second, the workflow moved off tokens entirely. All five packages — the umbrella included;
registering only four would break at the umbrella, last in dependency order, and leave a
partial publish — now name this repository and `publish.yml` as their trusted publisher on
npmjs.com, and the workflow authenticates by that identity instead of a secret. The token
injection and the `registry-url` setting were removed together (the `.npmrc` that setting
writes fails npm's config parsing when the env var is absent), and the pinned pnpm's OIDC
support was confirmed upstream before the switch. The workflow edit itself went through the
commit surface's witness — a `witnessed` row, commit `31fa0f7`. The range that remains is
finite: one token-free publish succeeds, and `NPM_TOKEN` is deleted.

## The debt that stays open

The first out-of-repository real-project install — a real project, real payloads, rows and
exit codes cited — did not happen in v0.3. The clean-environment e2e installs into a temporary
tree that exists for the test; a real project is a different claim, and this series does not
substitute one for the other. What remains is the choice of target project, and the item
stands as the first exit criterion of the next milestone's gate.

Two adjacent facts belong in the same honest paragraph. v0.3.0 was closed by owner decision
with the npm listing measured (all five packages at `0.3.0`, queried 2026-08-11), and its
journal round runs with the next milestone's gate rather than its own. And the pipeline's
publish step has still never succeeded as a pipeline — a human has proven the gates and the
upload separately, but the merge-to-registry path end-to-end is exactly what the next release
verifies.

## Solved-problem log

**We believed** checking the three preconditions — scope, token, secret — was as close to
verifying publish capability as one could get before publishing → **what happened**: the
registry's policy changed three days before the token was issued, the capability the
preconditions existed for was the one thing they could not attest, and the first upload
stopped at a prompt no CI can answer → **what we changed**: authentication moved from a secret
a human holds to an identity the registry checks — this repository, this workflow — where
there is no token to expire, revoke, or outlive a policy. The verification is the next release
itself, and the plan's own boundary held: what §3-e declared unverifiable by code was never
claimed as verified, so the failure was an event inside a known region, not a surprise outside
the map.

## The commitment for post #4

Two debts, each with a finite range. First, the real-project install: one project outside this
repository, installed from the registry, wired by `init`, judging real payloads — rows and
exit codes cited, or post #4 says it did not happen. Second, the token-free publish: the next
release either succeeds through the trusted-publisher path — reported together with the
`NPM_TOKEN` deletion that success authorizes — or the failure is quoted as this post quoted
`EOTP`.
