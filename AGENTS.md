# Polydeukes

`AGENTS.md` is the project-wide source of truth for every supported coding agent.
Before touching a path, read every applicable file in `.claude/rules/`; those path-scoped rules
apply to every coding agent working in this repository.
If `AGENTS.local.md` exists, read it after this file as additive machine-local context; it never
replaces the shared instructions here.

A development *discipline* framework for building alongside an AI coding partner — deterministic
covenants, a verifiable ledger, local memory, and adversarial verification on one thin core.

**This repo is beta** (since v0.7.0). Seven npm packages and one Rust crate ship today, alongside a
Python SDK:
`core` (the covenant protocol — stdin-JSON in, exit code out — with file-change evidence, the
config schema, the algebra declaration schema, the input IR schema, and the memory search
output schema), the three adapters
`adapter-claude-code`, `adapter-grok` and `adapter-codex` (each one agent's session payload
onto the
input IR, registration, and host response; the change-set surface is a unified diff on stdin that
the
umbrella translates itself), and the `polydeukes` umbrella (the `pdks` bin, `loadConfig`, both
surfaces' composition roots, the disk they need — and the judge itself as its `src/covenant/`
module: Bash analysis, path-routing dispatcher, meta-covenants, TTL witness, discipline
library, and the declaration engine — extract steps, seven relations, witness lists).
The umbrella depends on all three adapters; each adapter peers on core and exposes the same
three verbs: `prepareHook`, `registerHook`, and `renderHookResponse`. The common CLI owns
stdin, executable identity, process deadlines, and the single `pdks covenant check` child.
`pdks adapter <claude-code|grok|codex> init` pins the current executable and project root in
native host registrations. The adapters own payload translation, evidence, and host responses.
Codex normalises file edits that reach its hook into `apply_patch`, whose input is patch text;
the adapter translates it into one IR element per file. The three SDKs provide the same four process
verbs: covenant input, change set,
memory ingest, and memory search. Each language shares one executable resolver and byte
transport across its verbs: an explicit executable resolves against the caller's cwd;
otherwise the first executable `pdks` in an absolute PATH directory runs. The root sets the
child's cwd. SDKs return closed results, enforce an optional communication deadline, and
leave judgment, telemetry, and indexing to pdks.
`sdk-ts` (`@polydeukes/sdk-ts`) exposes `checkCovenant`, `checkChangeSet`, `memoryIngest`,
and `memorySearch` as asynchronous functions, with schema-generated input and search types
committed in `src/ir.ts` and `src/memory.ts`. It has no runtime package dependencies or peers;
core is a development dependency for tests. Its generator check compares both core schemas.
`sdk-rust` (the crate `polydeukes-sdk` on crates.io) exposes the same verbs in snake_case as
synchronous functions. Its types are generated by typify from core's
`covenant-input.schema.json` and `memory-search-output.schema.json` into committed
`src/ir.rs` and `src/memory.rs`. The umbrella's single executable contains Node and its bundle,
built by
`packages/polydeukes/scripts/build-sea.mjs` and attached to each GitHub Release by
`publish.yml`. The Rust crate has no `package.json`, so pnpm, turbo, and `pnpm test` do not
see it; CI runs `cargo test` after the build.
`sdk-python` (PyPI `polydeukes-sdk`, import `polydeukes_sdk`) offers the same four verbs
for Python 3.12+ with no runtime dependencies. One resolver selects an explicit executable or
the first executable `pdks` in an absolute PATH directory; all four verbs use that one process
contract. Its TypedDict wire types are generated from core’s two schemas. Python checks and
builds run through uv in explicit CI steps; pnpm and Turbo do not enumerate this package.
`node scripts/verify-sdk-contract.mjs --executable <absolute-pdks>` compares all three SDKs'
observations of the shared fixture, real judgments, telemetry, and ranked searches.
`memory` (`@polydeukes/memory`) splits markdown documents into section rows and
keeps them in a `node:sqlite` index (FTS5, trigram) at `.polydeukes/memory.db` that can always
be rebuilt from the documents. The umbrella declares it as an optional peer and loads it only
in `pdks memory ingest | search | show | obligations | supersession | lint | stats | usage`,
dynamically; the judgment
chain never imports it, and without it that command prints an install hint and exits 2. One
more directory, `packages/documentation`, is `private` and publishes nothing: it builds the
public site at <https://polydeukes.vercel.app> from `docs/` at build time and carries no judgment
logic.
The single executable bundles the three adapters. Their source packages depend on core;
the judgment module consumes their IR without knowing host payload fields. The judge module opens no
file at all, and core's only file I/O is the
telemetry log it appends every judgment to.
Details live in the code and the archived PRDs (the merged contracts).
The design docs own everything not yet implemented; when a design doc and shipped code disagree,
neither side wins by default — triage against the archived PRD: it may be a stale doc, or a code
bug to fix.

## Vocabulary is binding

This project deliberately renames control-framing terms. **Never use `guard`, `harness`, or `kb`**
in code, packages, CLI, or docs — use `covenant`, `discipline framework`, and `memory`. The full
glossary is in `.claude/rules/domain-terms.md` (scoped to `packages/**`); read it before
naming anything. One deliberate exception: the npm `keywords` array keeps the industry terms —
it is a discoverability index; the `description` field is NOT exempt.

## Conventions

- **Public docs are bilingual:** English is the default; Korean mirrors live in `*.ko.md`. Keep them
in
  sync when editing either — the change-set surface judges the pair (`docs-stay-bilingual`, advised
  when one side is staged without the other). In Korean docs, use translation + English gloss
  for the vocabulary (`약속(covenant)`), never transliteration. The repository instruction files
  `AGENTS.md` and `AGENTS.local.md` are exceptions and have no Korean mirrors. Internal
  documents under `_docs/`, including PRDs, are written in Korean only.
- `pnpm check` is the canonical "fix everything" command (Biome lint + format with `--write`).
- Root `pnpm test` completes workspace builds using Turbo's cache, then runs every package's
  test suite in parallel on each invocation. For a focused
  e2e run, first run `pnpm build`, then `pnpm -F <package> exec vitest run <file>`; focused
  tests consume the existing build artifacts. Typecheck before either build command.
- Do not use or introduce Transcodes in this repository. Do not invoke Transcodes plugins, skills,
  MCP tools, CLI commands, Persona workflows, hooks, generated files, or dependencies here. Manage
  agent instructions directly in this `AGENTS.md` and the repository-owned rule files.

**Path-scoped rules carry the rest.** Each file in `.claude/rules/` states the constraints a
file's own source does not explain. Before touching files, determine the intended paths, inspect
the `paths:` frontmatter of every rule, and read every matching rule in full. Repeat this check if
the change scope expands. Hosts that support `.claude/rules/` may load them automatically; all
other agents, including Codex, must perform this routing explicitly.

## How this project is developed

Development follows a roadmap → PRD → TDD loop, codified as skills: `/ticket <ID>` runs the full
unit-task loop and `/post-task` alone closes out substantial non-ticket chores before they
commit. Unit tasks must be small enough to fit one PRD and verifiable by a command or test.

**A gap left by a finished ticket is closed by a retrofit ticket, not a new roadmap ID**
(`COVENANT-01b` is the precedent): its own suffix, branch, and PR. Archived PRDs stay immutable;
the retrofit records the correction and the archived PRDs get a footnote pointing at it. This
keeps the roadmap a plan rather than a defect list.

Work that starts from an outside issue report takes its ID from the GitHub number instead
(`ISSUE-59`, split as `ISSUE-62a`), whether or not it closes a finished ticket's gap — the
report number is the stronger identifier, and the archived-PRD footnote still applies.

**Tickets live in Forgejo issues, not in a document.** Every planned ticket, candidate,
open-on-condition item, and observed friction is one issue on `b95labs/polydeukes`, titled with
its ID, labelled by kind, and placed on one of three kanban projects (roadmap, issue reports,
docs). A milestone's goal and Exit Criteria are its Forgejo milestone description, and the
milestone is named for its goal, not a version number. No wiki page duplicates them.

An outside report is first reproduced in a scratch repository with the released `pdks` bin,
and its verdict (accurate · partial · not reproduced · misreproduced) is posted as a comment.
It is then dispositioned one way: a doc chore (committed to `main`, report closed at once), an
`ISSUE-<n>` ticket — without waiting when leaving it costs a locked session, a discipline
silently off while rows read `passed`, or a declaration that can only answer one way — or a
`friction` issue carrying its re-evaluation trigger. Commits and PR bodies cite the report as
`huskyhoochu/polydeukes#<n>`; a bare `#<n>` resolves to a Forgejo number. A report is closed by
hand, with the version that shipped it.

**A milestone closes through a fixed gate**, once its Exit Criteria hold: ① a full audit runs
every criterion's command; ② a dogfooding journal round is added with numbers; ③ the
release-please PR merges; ④ `_docs/roadmap.history.md` gains the gate entry and inherits the
milestone's Exit Criteria verbatim.

## Self-dogfooding (ON since 2026-07-14)

Native PreToolUse registrations translate the supported file and shell calls, while lefthook's
pre-commit pipes `git diff --cached` into `pdks covenant check --diff`. Each registration pins
`.polydeukes/bin/pdks` and the project root; this executable bundles all three adapters and the
judge. Regenerate registrations with `pdks adapter <claude-code|grok|codex> init`, using the
installed executable, rather than editing generated handlers. Grok uses its native tool names
(`write`, `search_replace`, `run_terminal_command`); under Grok's runtime, the Claude
compatibility registration is silent and the Grok registration owns the judgment.

Measured on 2026-10-21 on macOS arm64: Claude Code 2.1.306 and Grok 1.0.62 allowed ordinary
file operations and blocked a protected write in scratch projects. Both registrations together
in Grok produced one self-mod block for that write. A missing executable blocked the Claude
write with `onFailure: block`; Grok proceeded without a judgment row. After this repository's
native cutover, Codex CLI 0.163.0 nested `apply_patch` allowed an ordinary file, blocked a
same-content protected-config patch, and refused a directory pre-state read failure with one
`blocked covenant-check` row. These observations cover those calls and versions; the outer
Code Mode dispatch itself has no established adapter payload.
Do not infer host-wide coverage from `/hooks` showing Active; remeasure the released host
version before claiming it.
Codex session evidence comes only from the registered `UserPromptSubmit` and `PostToolUse`
lifecycle events, is removed at `SessionEnd`, and never comes from the unstable transcript.
Claude and Codex admit prompt text as human evidence only with explicit human origin; Grok
supplies no human-message evidence. Without proven human evidence, perform a protected
intentional change from the user's terminal.

Session-protected: the gate definitions (hook wiring, `.claude/settings.json`, `lefthook.yml`,
`biome.json`, `.git/hooks`), the packages' gitignored `dist`, and the root config. This includes
the Codex hook directory, `.codex/hooks.json`, `.polydeukes/bin/pdks`, and adapter dist. The
change-set surface has no list of its own and no prompt: it judges the piped diff and lands every
verdict `advised` at exit 0 unless the command carries `--enforce block` (this repo's lefthook
line does not — a staged gate-file change has already passed the session surface). Disciplines
sit in three lists — `disciplines:` (both surfaces), `sessionDisciplines:` (one live call),
`changeSetDisciplines:` (a finished change set) — and the loader refuses an entry written in a
list whose surface cannot observe its channels; each surface compiles the shared list plus its
own. A break lands `advised` (exit 0, the `why` on stderr) unless the entry says
`enforce: block`. The session-protected list is a separate
list, not an override applied to those entries: nothing promotes a discipline's own `advise`
to a block, and since POSTURE-01 the protected list above is the only thing that blocks
unasked — on the session surface. Every judgment appends one row to `.polydeukes/roi.log`
(local, gitignored).

**What each axis compares, and the witness valve, are in
`.claude/rules/dogfooding-axes.md`** — read it for the hook, the config, and the judge packages.
The recovery procedures below stay here because no `paths` glob can predict when a session locks.

### Recovery and rewiring

- The session hook runs the pinned executable independently of workspace `dist` and
  `node_modules`. Typecheck sources before building. Rebuilding the workspace updates the
  development CLI and lefthook's judgment; the pinned session executable is updated separately.
- Build a replacement executable at a temporary path and run
  `node scripts/verify-adapter-executable.mjs --executable <absolute-path>` before replacing the
  protected installed file. Keep the current executable available until its replacement is
  proven. Root configuration and hook definitions remain protected owner changes.
- If the installed executable or configuration cannot load, recover from the user's terminal.
  An assembly failure occurs before the witness valve can run. Preserve the witness token and
  TTL while repairing the executable, config, or wiring.
- A changed Codex hook definition needs user review through CLI `/hooks`. After init and trust
  approval, measure ordinary and protected calls and inspect telemetry; an Active label alone
  does not establish that the host invoked the hook.

The measured history behind these rules lives in the local knowledge store.
